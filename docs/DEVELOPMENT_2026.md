# Разработка версии 2026

## Ветки и контрольная точка

`main` — старая стабильная production-версия, запрещённая для текущей разработки. GitHub default branch остаётся `main`. Исходный commit: `ab8119ac4495e6994e3730f83e9a8a9121967a80`. Annotated tag `legacy-pre-2026` сохраняет именно этот commit; его нельзя перемещать или перезаписывать.

`develop-2026` — интеграционная ветка новой версии, созданная от того же commit. Новая версия наследует существующий сервис, а не создаётся с нуля. После создания различия с main допускаются только в development-линии.

## Имена и рабочий процесс

Используйте `feature/<короткое-название>`, `fix/<короткое-название>`, `refactor/<короткое-название>`, `chore/<короткое-название>`. Например: `feature/new-home`, `feature/sidebar`, `feature/print`, `feature/photobank`, `feature/pdf-preflight`, `feature/admin`, `fix/template-loading`.

Перед работой проверьте status, обе diff и отсутствие риска перезаписи локальных файлов. Обнаружив неожиданные пользовательские изменения, остановитесь. `0_documents.zip` и `0_documents/` разрешено оставлять untracked: не изменять, не перемещать, не индексировать и не добавлять в tracked `.gitignore`.

Для новой задачи на безопасном рабочем дереве:

```bash
git fetch origin
git switch develop-2026
git merge --ff-only origin/develop-2026
git switch -c feature/short-name
git merge-base HEAD origin/develop-2026
```

Проверьте, что новая ветка начинается на актуальном `origin/develop-2026`. Одна крупная задача — одна ветка; по возможности один Codex task/thread. Сначала изучите существующее решение, определите переиспользование и краткий план, затем реализуйте задачу, проверьте и проведите self-review. Индексируйте только конкретные проверенные файлы.

## Pull Requests

Все рабочие PR направляйте явно в `develop-2026`, даже если интерфейс GitHub предлагает `main`:

```bash
git push -u origin feature/short-name
gh pr create --base develop-2026 --head feature/short-name
```

Перед merge проверьте полный diff, отсутствие секретов и случайных файлов, результаты применимых проверок и актуальный base PR. Завершённые feature/fix/refactor/chore ветки сливаются только в `develop-2026`. Не удаляйте существующие ветки без необходимости и разрешения.

PR #1 (`codex/plugin-setup`) перенаправлен с `main` в `develop-2026` при подготовке. Он оставлен открытым: его AGENTS.md содержит менее строгие правила main и пересекается с новыми инструкциями. Перед возможным merge согласуйте его содержимое с корневым AGENTS.md и проверьте актуальность скрипта установки плагинов. Не запускайте этот скрипт как часть подготовки сервиса.

## Защита main и финальный выпуск

Для `main` включены обязательный PR, применение правил к администраторам, запрет force push и удаления, разрешение обсуждений перед merge. Обязательные status checks не добавлены; обязательных одобрений reviewer — 0. Эта защита не заменяет правило отдельного разрешения владельца: она не подтверждает готовность 2026 и технически не запрещает каждый возможный merge через PR.

Новая версия может попасть в main только после полной готовности, полного тестирования и отдельной прямой команды владельца о замене production версией 2026. До этого не создавайте release PR в main и ничего туда не сливайте.

При будущей явно одобренной финальной замене:

1. Зафиксировать проверенный кандидат из `develop-2026`, провести build, применимые lint/tests, функциональные, визуальные и security-проверки.
2. Проверить совместимость storage/API/Figma, подготовить резервные копии внешних данных и план отката, если нужны миграции.
3. Получить отдельную прямую команду владельца на production replacement для конкретного кандидата.
4. Создать и проверить единственный финальный PR `develop-2026` → `main`, соблюдая защиту ветки; не использовать force push.
5. Выполнить согласованный выпуск, проверить production-сценарии и сохранить legacy tag.

## Vercel: Production и Preview

Желаемое состояние: `main` → Production; `develop-2026` и `feature/*` → Preview. Не переключайте GitHub default branch и Vercel Production branch на develop. Не меняйте production env и не выполняйте production deployment новой версии без отдельного разрешения.

При подготовке Vercel MCP недоступен: связь проекта, фактическая Production branch и включение Preview не подтверждены. В Vercel проверьте Git-связь с `Aexaxaxa/cherkizovo-design-service`, Production branch/environment tracking и Preview для рабочих веток. Если Production branch отличается от main, сначала сообщите владельцу; автоматически не исправляйте.

## Восстановление старого исходного кода

Проверьте tag и его SHA, затем создайте отдельный каталог восстановления, предварительно убедившись, что такой каталог не существует:

```bash
git fetch origin
git rev-parse 'legacy-pre-2026^{commit}'
git worktree add --detach ../cherkizovo-legacy-recovery legacy-pre-2026
```

Ожидаемый SHA: `ab8119ac4495e6994e3730f83e9a8a9121967a80`. Эта процедура восстанавливает Git-исходники и не переписывает main. Используйте lockfile для зависимостей. Секреты и внешние B2/Figma/Yandex Disk данные не входят в Git tag: для полного восстановления работающего окружения потребуются отдельно сохранённые настройки и данные. Любой production rollback требует отдельной команды и согласованной процедуры; не применяйте reset/force push к main.

## Codex

Основные постоянные правила находятся в `AGENTS.md`. Приоритет: reuse > improve > refactor > replace. Используйте доступные применимые skills; не выдавайте отсутствующие плагины за установленные. Для code changes выполняйте production build и рабочие lint/tests; для UI — запуск и browser QA. Для документации проверяйте содержание, diff и Git ancestry. В отчёте указывайте ветку, файлы, проверки, commits, PR/base и оставшиеся ограничения.
